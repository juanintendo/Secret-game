## Ranking rationale

**Why R1 is first.** The binding constraint on this project is authored character action, not code. Every risk below it can be fixed with time; R1 *is* time. It is also the only risk that got measurably worse since the last consultation, because each new sheet added rig features rather than removing them.

**Why R5 has no validation experiment.** It is a discipline risk. There is no test that tells you whether you started art too early — you find out when the combat design changes and the models are wrong. The mitigation is a gate, and gates only work if someone enforces them.

**Why R22 is high probability.** Because it already happened. An obsolete image sitting unlabelled next to canonical ones is not a hypothetical failure mode on this project; it is a documented one, and the file is still there.

**Why R29 is high probability despite being a policy the team has explicitly chosen.** Not because anyone intends to abandon it, but because a quality floor with no named machine attached cannot be measured, and unmeasured commitments erode under schedule pressure by default rather than by decision. Naming the minimum hardware (Q30) converts it from an intention into a test. That is the whole mitigation.

**Why R11's closure is worth keeping visible rather than deleting.** The risk was recorded because I misread a character sheet at reduced scale — the same class of error that produced four wrong findings in the previous consultation. The register entry stays as `CLOSED` so the pattern is legible: **this project has now lost time twice to visual facts asserted without magnification.** Gate 10 in consultation §11.9 exists because of it.

**Why the engine risks (R16–R18) rank low on probability but high on impact.** Each is individually likely to pass. But R16 is the assumption the entire engine choice rests on, and if it fails after six months of Unity work the cost is a migration, not a fix. That is what the spike exists to prevent.
